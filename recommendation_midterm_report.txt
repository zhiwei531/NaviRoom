NaviRoom Recommendation Module Midterm Status Summary

Section 1. Overall Status

At the midterm stage, the NaviRoom recommendation module has progressed from a lightweight prototype into a substantially more proposal-aligned component. Its current purpose is to recommend suitable rooms under cold-start conditions, especially when a newly uploaded institutional dataset has incomplete structure or limited historical reservation data. The module is no longer just a keyword-based baseline. It now combines semantic room understanding, booking-window awareness, and temporally weighted reservation behavior into one ranking pipeline, which makes it much closer to a deployable recommendation core for the larger NaviRoom system.

Section 2. Core Algorithm Design

The current algorithm can be understood as a multi-stage recommendation pipeline. It begins with hard constraint filtering, where rooms are screened by capacity, room type, required equipment, and, when applicable, booking-window availability. After this first stage, the system enriches each room profile by merging room-side metadata with reservation-side descriptions. This enrichment is critical because the raw data are heterogeneous: canonical fields may be generic, incomplete, or inconsistent, while useful semantic signals are often hidden in raw text.

The semantic matching stage is the main innovation in the current recommendation design. Instead of relying only on direct lexical overlap, the system now performs local semantic recall using normalized text, alias expansion, and derived use-case features. This allows the engine to connect user intent with room semantics even when the wording does not exactly match the stored metadata. For example, the system can map “monitor” to “screen,” connect “video practice” to booth-like spaces, and infer that a “multi-media booth” remains semantically relevant even if the dataset stores that room under a more generic type label. This is important because the proposal explicitly emphasizes zero-shot recommendation under heterogeneous metadata conditions, and the current algorithm directly supports that objective.

To further improve semantic quality without making the system too expensive to deploy, the module now uses bounded LLM reranking. The algorithm first performs local recall over all filtered candidates, then selects only a shortlist of the strongest rooms for LLM-based semantic reranking. This means the module can still benefit from deeper semantic reasoning while keeping API cost and latency under control. In practical terms, this Top-K reranking strategy is one of the strongest algorithmic innovations implemented so far, because it balances semantic quality with engineering realism rather than optimizing only one side.

The behavior component has also become algorithmically more meaningful. Instead of treating all historical reservations equally, the system now applies recency-weighted scoring so that recent booking behavior contributes more strongly than stale history. This affects popularity, time-slot preference, and duration preference, and it aligns the module with the proposal’s interest in temporal weighting and adaptive recommendation. The result is a ranking model that is not only content-aware, but also more responsive to current usage patterns.

Section 3. Major Completed Improvements

The most important completed improvements since the earlier baseline are:
- zero-shot semantic recommendation through room-profile enrichment, alias recovery, local semantic recall, and optional LLM reranking;
- availability-aware filtering through explicit `requested_start` and `requested_end` support, allowing the engine to exclude rooms with conflicting reservations;
- recency-weighted behavior modeling, so the recommendation process reflects recent demand rather than flat historical counts;
- bounded Top-K LLM reranking, which keeps semantic refinement deployable in terms of latency and cost.

These changes collectively shift the module from a shallow lexical recommender toward a hybrid recommendation algorithm that is much closer to the proposal’s intended contribution.

Section 4. Engineering Integration Status

From a system perspective, the recommendation module is now in a relatively strong intermediate state. It exposes stable Python integration points through `recommend_from_dataset_json(...)` and `recommend_rooms_payload(...)`, and the repository documentation now specifies the intended backend route contract for a future `POST /api/recommendations` endpoint. This means the backend wrapping work has been largely prepared at the interface level, even though the full route implementation is still pending.

The frontend is not yet fully connected to this recommendation engine, but the request and response contracts are already documented. As a result, the recommendation module is no longer isolated experimental logic; it is now structured in a way that allows clean integration into the broader NaviRoom architecture.

Section 5. Validation and Evidence

Validation at this stage has been practical and targeted rather than fully automated. Because the current server environment does not include `pytest`, the module has been checked through compilation validation, manual regression assertions, synthetic behavior tests, and real dataset checks using the DKU data. The main verified behaviors are:
- successful zero-shot recovery of multi-media booth recommendations;
- successful semantic mapping from user terms such as “monitor” to room features such as “screen”;
- exclusion of rooms whose reservations overlap with a requested booking window;
- stronger ranking influence from recent reservations than from stale reservation history;
- correct limitation of LLM reranking calls under the Top-K shortlist strategy.

These checks provide good evidence that the recommendation pipeline is functioning as designed, although a full automated test suite is still a necessary next step.

Section 6. Remaining Gaps

Although the recommendation module is much stronger than before, it is not yet a complete intelligent scheduling system. The current implementation produces ranked suggestions and can filter out unavailable rooms, but it does not yet perform multi-request optimization, fairness-aware allocation, or explicit diversification across competing users or high-demand rooms. This distinction is important for the midterm report: the project has already achieved a meaningful recommendation innovation, but it has not yet fully realized the broader scheduling and allocation ambitions described in the proposal.

Another limitation is that the frontend remains a prototype and has not yet been fully connected to the backend recommendation path. In addition, while the LLM reranking stage is now bounded and better engineered, it still depends on external model quality and API availability. Finally, the current validation process is credible for development purposes but not yet as rigorous as a full automated evaluation pipeline.

Section 7. Midterm Conclusion

The recommendation module should be presented in the midterm report as one of the clearest technical advances of the project so far. Its most important innovation is the algorithmic transition from simple lexical matching to a hybrid recommendation pipeline that combines semantic room understanding, zero-shot reasoning, availability-aware filtering, recency-weighted behavior modeling, and bounded LLM reranking. This is significant because it directly addresses the proposal’s central challenge: how to recommend rooms intelligently in data-scarce and structurally inconsistent environments.

In summary, the current module is no longer just a proof-of-concept baseline. It has become a credible recommendation core with a clear algorithmic contribution, practical deployment awareness, and a defined integration surface for the rest of NaviRoom. The next stage of work should focus on full backend integration, frontend integration, richer evaluation, and broader scheduling or fairness extensions, but the recommendation component itself already provides strong material for the midterm report, especially as an innovation-focused section of the project.
