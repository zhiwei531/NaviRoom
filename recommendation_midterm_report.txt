NaviRoom Recommendation Module Midterm Status Summary

The recommendation module in NaviRoom is currently positioned as a cold-start room suggestion component for heterogeneous institutional datasets. Its main purpose is to recommend suitable rooms even when a newly uploaded organization has limited historical booking data, while still taking advantage of reservation behavior when such data exist. At the midterm stage, the module has moved beyond a simple prototype and now reflects the main recommendation-oriented goals described in the proposal, especially the emphasis on zero-shot reasoning, adaptive semantic interpretation, and practical deployability.

The current recommendation pipeline can be understood as a layered ranking process. It begins with hard constraint filtering, where candidate rooms are screened by capacity, room type, and required equipment. Unlike the earlier version, room type is no longer limited to a single canonical field. The system now recovers aliases and latent semantics from raw room metadata and reservation-side text, which is important because the underlying data are not consistently structured. A room that is stored under a generic label can still be interpreted correctly if its raw description indicates that it is, for example, a multi-media booth.

On top of this filtering stage, the module now performs room-profile enrichment. Instead of treating each room as a shallow record, it merges room-side metadata with reservation-side descriptions and uses the combined information to infer richer semantic features. This allows the engine to derive use-case signals such as online meeting, video practice, quiet study, brainstorming, and online interview. The practical effect is that rooms can be matched to user intent even when the user query does not use exactly the same wording as the source data. This enrichment step is one of the main reasons the module is now much closer to the proposal's zero-shot recommendation objective.

The semantic matching stage has also become substantially stronger. The previous version relied too heavily on lexical overlap and therefore behaved more like a keyword matcher than a true semantic recommender. The current version first performs local semantic recall using normalized text and hand-built semantic alias expansion. This means that queries such as “monitor” can be mapped to “screen,” while requests related to video practice, private calls, or online interviews can be associated with booth-like spaces or quiet rooms when appropriate. This local recall path guarantees that the module can still function even if external LLM service is unavailable.

To improve semantic precision without making deployment costs unreasonable, the module now uses bounded LLM reranking rather than broad LLM scoring across all candidates. After local semantic recall identifies the most relevant rooms, only a limited shortlist is passed to the LLM for deeper semantic reranking. This shortlist size is controlled by the `RECO_LLM_TOP_K` environment variable. The result is a more realistic tradeoff between quality and cost: the system retains the benefits of LLM-based semantic refinement, but avoids the unstable latency and API expense that would come from scoring every candidate room through the model.

Another major improvement is that recommendation is no longer purely about suitability in the abstract. The earlier implementation could suggest rooms that matched a query semantically but were not actually usable at the requested time. The current module now supports explicit booking-window inputs through `requested_start` and `requested_end`. When these fields are provided, the engine automatically derives time-slot and duration context and checks for reservation overlap before ranking candidates. In other words, recommendation is now availability-aware. This makes the recommendation component much better aligned with the broader scheduling direction in the proposal, because a room can now be excluded before ranking if it is already occupied during the requested window.

The behavior-based part of the ranking has also been revised to better reflect temporal demand. In the earlier version, historical usage was counted in a flat manner, so an old booking and a recent booking had essentially the same influence. That was not consistent with the proposal’s emphasis on recent activity and temporal preference modeling. The current implementation uses recency-weighted behavior scoring, applying a half-life decay so that recent reservations influence popularity, time-slot affinity, and duration preference more strongly than stale history. This makes the recommendation output more adaptive to current usage patterns and more defensible as a real institutional system rather than a static heuristic ranker.

At the integration level, the recommendation module is now in a stronger engineering state than it was at the beginning of the semester. It exposes clean Python entry points through `recommend_from_dataset_json(...)` and `recommend_rooms_payload(...)`, and the repository documentation now defines the intended backend contract for a future `POST /api/recommendations` route. The frontend is still a prototype and is not yet fully wired to this interface, but the request and response contracts are already documented, which means the recommendation engine is prepared to be wrapped by a real backend service without needing its core logic to be redesigned again.

Validation at this stage has been practical rather than fully automated. Because the current server environment does not include `pytest`, the module has been verified using compilation checks, targeted regression assertions, synthetic test cases, and real dataset checks on the DKU data. These validations covered the most important functional improvements: zero-shot retrieval of multi-media booth rooms, semantic mapping from monitor to screen, removal of overlapping rooms under a requested booking window, preference for recent usage over stale history, and bounded LLM reranking behavior. This is enough to support a credible midterm claim that the recommendation module has been substantially improved, although a more formal automated testing layer remains necessary for the second half of the project.

At the same time, the module is not yet a complete scheduling optimizer. It now performs recommendation under constraints and can exclude unavailable rooms, but it still operates as a ranked suggestion engine rather than a full multi-objective allocation system. It does not yet explicitly optimize fairness across users, diversify results beyond the strongest candidates, or allocate rooms jointly across multiple competing requests. These are important limitations to state clearly in a midterm report, because they distinguish what has already been achieved from what remains part of the project’s later-stage ambition.

Overall, the recommendation module is now in a strong intermediate state. It has evolved from a simple lexical-and-history prototype into a more proposal-aligned system that combines zero-shot semantic recommendation, metadata enrichment, scheduling-aware availability filtering, recency-weighted behavioral modeling, and bounded LLM reranking. This means the module is already useful as a deployable recommendation core, even though the full end-to-end system described in the proposal still requires backend integration, frontend integration, broader evaluation, and further work on fairness and scheduling optimization. For a midterm report, the most accurate characterization is that the recommendation module has achieved its core technical transition: it is no longer merely a proof of concept, but it has not yet become the final production-grade intelligent scheduling system envisioned by the full project.
